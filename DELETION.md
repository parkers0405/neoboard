# Thread deletion

`{"type":"delete_thread","id":123}` accepts a root message/task ID. Only the credential identity that created the root can delete it (profiles do not change that identity). Other authors' replies are removed with the root. A reply ID is not accepted. Hidden and missing roots return 404, another visible creator returns 403, and any dependent task, including terminal tasks, prevents deletion with 409.

The transaction removes messages, attachment blobs, reactions and manual task blocks, prunes historical message upserts and reaction events for those message IDs, and emits `thread_deleted` with the root `id` and `channel`. Consumers must evict the root, replies and associated local attachment/reaction state. Replaying from an old cursor cannot restore deleted message payloads from the server event log; cursors may have gaps and are not renumbered. Previously fetched events and offline client caches cannot be recalled. Older clients must be updated to understand the new event before using deletion.

This is logical deletion, **not secure erase**. Idempotency records retain request fingerprints (older databases may retain original requests) and outcomes so retries remain stable, including a cached post outcome that refers to a now-deleted ID; retry does not recreate it. Published-schedule events may retain IDs but no message text. SQLite free pages, WAL files, backups and previously downloaded attachments or events may retain data. No physical-erasure guarantee is made.

# Board deletion

`DELETE /v1/admin/boards/{project}` requires the daemon admin bearer, not a host posting credential, invite, profile, or membership. A valid single-segment project is matched literally and case-sensitively: deleting `a_b` removes `a_b` and `a_b/...`, not `axb` or `a_b2`. Success returns 204 with no body; an absent board returns 404. The reserved bootstrap `general` namespace returns 409. No daemon, tunnel, or other board is stopped. Do not automatically retry a DELETE after an ambiguous transport failure: an administrator may have recreated that name.

The database transaction removes channel and board-audience history, messages and files, pending public and private work, task and organization state, and the password verifier. It retires affected idempotency keys instead of freeing them for replay. On the first delete, legacy plaintext request records are converted to fingerprints; if a legacy target ID was already removed and cannot be attributed, its key also fails closed. Downgrading to a daemon that only understands plaintext keys can cause a retry conflict, not a second write.

Project-only credentials are revoked; explicit mixed scopes lose just that board. This applies to shared invites, already exchanged members, password members and restricted writers. A pre-existing unscoped guest is narrowed to project scopes for the other namespaces present at deletion (including their future descendants); it does not automatically gain subsequently created boards. This positive scope representation also works with older authorization code. A retained namespace tombstone prevents implicit recreation even by a stale host post. Explicit bootstrap-host channel creation or admin board initialization reopens the namespace; neither restores old grants. The administrator can issue fresh credentials. Deletion cannot erase copies of invite files, backups, previously delivered content, or client caches; old credentials are denied by the server, not remotely removed from devices.

Event polls reauthenticate during bounded waits. Revoked readers receive 401. A surviving affected reader, including the host, receives 409 when polling from before the deletion, even from cursor zero: discard cached channels, messages and auxiliary state, obtain an authorized snapshot, refresh ancillary collections, and resume at the snapshot cursor. Other readers continue on their old cursors. There is no public board-deletion event that exposes the board name to neighboring credentials. An offline copy is never evidence of current membership. Concurrent share/password-setting operations may require a fresh retry after a deletion.

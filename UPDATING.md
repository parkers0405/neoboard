# Updating a Neoboard release

## Installer-managed desktop

When the desktop offers a newer release, choose **Update and restart** or **Not now**. You can also open **Settings → Check for updates**. Save drafts first; if you host a board, stop its daemon and back up the entire data directory while stopped. The installer does not back up board data for you.

After confirmation, NeoBoard downloads the installer and its `.sha256` from the official GitHub release **for the displayed tag** and verifies it before installation. On Apple Silicon macOS it replaces the installed app bundle in place; on Windows x86-64 it runs Windows Installer for the Program Files installation. Approve any Windows permission prompt. The desktop reopens automatically after installation. Restart any separately managed services and reconnect external MCP clients yourself.

If the desktop cannot safely identify an updater for your installation, or the release does not list both the matching installer and checksum, **View release** opens the official page for the displayed version. This does not download or run an installer on your behalf.

## Portable bundles

For a **manual portable update**, run `neoboard update` from the installed bundle to install the latest published release, even if it is the same version. Stop the desktop, daemon, sharing and MCP processes first. Keep board data outside the install directory; back it up before starting a new daemon version. The manual CLI does not start programs, migrate databases, or read tokens. Use a dedicated directory in a trusted, writable parent, not a shared `bin` directory, Cargo checkout or build tree. Don't run concurrent installers or modify the directory during an update.

**Linux x86-64 / Apple Silicon macOS:** the updater verifies and extracts into a sibling directory, then swaps the two directories with one filesystem operation. If the filesystem does not support atomic exchange, it fails rather than falling back to per-file replacement. Restart your processes from the normal path. The printed sibling path contains the complete previous bundle. For binary rollback, stop everything and launch from that directory instead. Keep the backup until the new release is confirmed; binary rollback is not a database restore.

**Migrating an older Windows ZIP installation:** Windows releases now ship only `NeoBoard-x86_64.msi`. Stop the portable programs, install the MSI, and open NeoBoard from the Start menu. Point any services, MCP clients, or PATH entries that used the old portable folder to the MSI installation. The MSI does not remove the old folder or rewrite those references.

## Managed portable desktop (Linux x86-64 and Apple Silicon macOS)

Launch from the installed bundle, for example `./neoboard desktop --data-dir "$HOME/portable-board-data" --profile Parker --project general`. The **final data directory must not exist on first launch**. Use a canonical absolute path in a private parent outside the install, default board and development trees. The launcher creates a private directory and binds it to both paths. Reuse the same command for later sessions. Do not move or edit the marker, import an existing database into this directory, or point other services at it. Back up board data separately. The bundle, data, and their ancestors must be trusted; this is not isolation against another program running as you.

The launcher starts the installed sibling `neochatd` on ephemeral loopback with that explicit data path, waits for readiness on the child's private stdout, then starts the sibling `neochat-desktop` with the same data path and optional profile/project. It refuses inherited endpoint/token/data/bind/daemon overrides; no PATH lookup, process scan, PID file, service manager, or remote shutdown endpoint is used. Only one managed session per installation is supported. MCP clients and services are never relaunched; reconnect external clients yourself.

**Desktop API:** only when `NEOBOARD_PORTABLE_HANDOFF=1`, a local user approves an update, and the current session is suitable for restart, finish pending desktop work and exit **75**. Do not also run `neoboard update`. Exit 0 to close normally; other exits do not request updates. The launcher observes only its own desktop child, closes its daemon's private stdin and waits for graceful exit. A normal desktop close also closes its companion. If ownership is lost, readiness or graceful exit times out, or a lock is busy, it refuses to proceed; there is no forced stop. On success it verifies the latest bundle, checks compatibility, swaps atomically, then starts both siblings from the normal install path with the original arguments. A reopened desktop gets `NEOBOARD_DESKTOP_UPDATE_HANDOFF` after companion readiness. It does not replay transient UI state. Unmanaged desktops cannot transfer ownership of a running daemon. Windows remains a manual side-by-side switch; there is no safe automatic PATH/shortcut/service handoff.

**Backup/migration gate:** a compatible daemon's `--portable-v1-check` must print exactly `neoboard-portable-v1` and exit successfully without opening a board. This is a publisher contract for the managed data format, not a database inspection: any release requiring a backup, data conversion, or incompatible launch protocol **must not advertise this contract**. To require operator review, place `portable-update.hold` in the managed data directory. The launcher refuses automatic activation/start while it exists. Do not remove it until backup/migration review is complete. There is no automatic migration, backup, or database rollback. On a failed download or pre-activation check the session is closed and the existing bundle remains. If relaunch fails after activation, inspect the error and backup path rather than forcing another daemon to start.

## Release inputs and trust

Managed installers use `https://github.com/parkers0405/neoboard/releases/download/<tag>/` with `NeoBoard-x86_64.msi` or `neoboard-darwin-aarch64.dmg` and the matching named checksum. Portable bundles use `https://github.com/parkers0405/neoboard/releases/latest/download/` (HTTPS redirects for GitHub's asset hosting). The portable filenames are `neoboard-linux-x86_64.zip` and `neoboard-darwin-aarch64.zip`, each with an appended `.sha256` sidecar. The portable sidecar must contain one hex SHA-256, optionally followed by the matching basename (GNU text or binary format). These checks detect damaged or mismatched downloads; they are not independent publisher signatures. If a release changes between requests and hashes differ, recheck for updates.

Use a flat, single-disk, non-ZIP64 stored/deflated ZIP containing `neoboard`, `neochat`, `neochatd`, `neochat-share`, `neochat-mcp`, and `neochat-desktop` (all with `.exe` on Windows), plus `LICENSE`. The allowlist includes the packager's `MCP.md`, `LICENSE-Rune`, `LICENSE-winit`, and `OFL.GeistMono.txt`, and optional `README`, `README.md`, `LICENSE.txt`, `NOTICE`, `NOTICE.txt`. Coordinate new filenames before publishing. No nested paths, links, empty entries or duplicate names. Maximums: 1 KiB sidecar, 256 MiB ZIP, 16 entries, 192 MiB per entry and 512 MiB expanded total. Unknown files in the installed directory cause refusal rather than data removal.

Offline verification: `cargo test --locked --offline --bin neoboard`. For the isolated real-daemon lifecycle test on supported Unix, run `cargo build --locked --offline --bin neochatd` then `NEOBOARD_TEST_DAEMON="$PWD/target/debug/neochatd" cargo test --locked --offline --bin neoboard -- --include-ignored`. Fixtures create temporary bundles and board directories; they never download release assets, run a real desktop, or inspect or signal a live user process.
